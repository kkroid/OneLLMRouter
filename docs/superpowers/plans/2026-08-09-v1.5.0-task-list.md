## Contract Rules

- The approved product design is authoritative. A Task may not reinterpret product behavior.
- Each Task owns only its declared write scope. Reading other files is allowed; writing outside scope is not.
- A Worker must commit its implementation and report the full HEAD plus the listed verification evidence.
- A missing or contradictory decision is `design_gap`; the Worker must not resolve it by expanding scope.
- Tests use `httptest`, temporary directories, or dynamic loopback ports. They must not contact or stop the active Router.
- No Task may add Auto Failover, MCP, Skill, or Prompt management.
- Integration is serial even when implementation Tasks are independent.

## T7: Core Configuration Commands

**Goal:** Provide secret-safe Core commands for Qt Provider/model read, validation, and atomic apply.

**Dependencies:** T5.

**Write scope:**

- `cmd/onellm-router/config_get.go`
- `cmd/onellm-router/config_get_test.go`
- `cmd/onellm-router/config_validate.go`
- `cmd/onellm-router/config_validate_test.go`
- `cmd/onellm-router/config_apply.go`
- `cmd/onellm-router/config_apply_test.go`
- `cmd/onellm-router/main.go`
- `internal/config/config.go`
- `internal/config/config_test.go`

**Required contract:**

- `config-get --json` returns only the editable `providers`, `codex.models`, and `model_slots` snapshot;
  each Provider exposes `api_key_set` instead of the stored `api_key`.
- `config-validate --json` reads the proposed editable snapshot from stdin and returns
  `{"valid": boolean, "errors": [{"field": string, "message": string}]}` without writing.
- `config-apply --stdin-json` accepts the same snapshot, validates it, writes the exact pre-apply YAML to
  the sibling `<config>.bak`, and atomically replaces the selected YAML.
- Apply modifies only `providers`, `codex.models`, and `model_slots`; Server, Log, global Proxy, Retry,
  and every other section remain untouched.
- Unknown fields and existing comments survive edits within the managed sections.
- Provider `prefix` is the identity used for secret preservation. An omitted `api_key` preserves the old
  key for the same prefix; a changed or new prefix must provide `api_key` explicitly. `api_key_set` is
  output metadata and never supplies secret input.
- The backup is a secret-bearing, restorable pre-image: it retains the old API key and source file mode,
  never contains the proposed replacement key, and is never echoed or logged.

**Non-goals:** No Server/Log/global Proxy/Retry editor, generic configuration framework, reflection-driven
schema merger, hot reload, Qt UI, credential vault, or modification of an external attached Core.

**Acceptance:**

- Failure at parse, validation, backup, or replace leaves the original config unchanged.
- Secret-leak tests prove stdout, stderr, logs, and validation errors contain neither old nor proposed API
  keys; backup tests prove the exact old YAML/key is retained, the proposed key is absent, and permissions
  are not broadened where the platform exposes file modes.
- Existing configuration loading and validation tests remain green.

**Verification:**

```text
go test -count=1 ./internal/config ./cmd/onellm-router
go test -race -count=1 ./internal/config ./cmd/onellm-router
git diff --check
```
