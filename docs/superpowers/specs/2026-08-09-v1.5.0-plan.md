# OneLLMRouter v1.5.0 产品与实施规划

> 状态：已批准进入执行（2026-08-09）
>
> 基线：v1.4.1
>
> 目标：让用户在 Claude Code、Codex 等客户端中一次配置多个供应商，随后只从原生模型列表选择 `provider/model`，同时能够查看各 Provider 和模型的 Token 使用量。

## 1. 版本决策

OneLLMRouter 的核心定位是：**所有供应商同时在线，只切模型，不切配置。**

用户在配置文件中完成 Provider、模型和协议入口的配置后，客户端始终连接同一个 OneLLMRouter。不同供应商以命名空间模型的形式同时出现在客户端的 `/model` 列表中，用户不需要在使用过程中修改客户端配置文件，也不需要打开额外的 Provider 切换器。

v1.5.0 围绕这一定位交付四项工作：

1. 采集 Provider/模型 Token Usage，并提供按天、周、月的统计。
2. 建立 Go Core 与 Qt Desktop 的跨平台基础边界，移除当前源码和构建中的 Windows 假设；本版本不交付完整的 macOS/Linux 安装体验。
3. 在 Qt 界面中配置 Provider 和模型，并由 Core 负责校验与写回配置。
   在此基础上补齐 Claude Code 与 Codex 的客户端配置辅助：客户端只需配置一次，
   后续从 OneLLMRouter 维护的模型列表中选择；客户端配置文件的写回必须保留用户已有内容。
4. 保持现有显式重试策略；只有在回归测试或真实故障证据表明有收益时，才做局部优化。

除以上产品工作外，v1.5.0 发布前增加一项工程收尾：将 Go 工具链升级到 1.26.x 最新稳定补丁版。该项只更新项目的 Go 最低版本声明和 CI/发布验证环境，不引入新的 Go 语言特性，也不顺带升级第三方依赖。

## 2. 范围与非目标

### 2.1 本版本范围

- Anthropic Messages、OpenAI Chat Completions、OpenAI Responses 三类请求的 Usage 统一采集。
- 流式和非流式、直通和协议翻译路径均纳入采集。
- Usage 按 Provider、请求模型和上游实际模型聚合。
- 提供日、周、月查询；周使用 ISO 周定义。
- Qt 主窗口提供 Providers、Models 和 Usage 页面。
- Qt 主窗口提供 Clients 页面：Claude Code 支持受控的 settings.json 合并；Codex 展示
  config.toml/catalog 状态、有效模型来源和同步状态，并仅编辑明确属于 OneLLMRouter 的设置。
- Go、Qt、构建脚本和 CI 具备平台隔离和编译矩阵。
- 现有 Retry 的边界测试、Usage 与 Retry attempt 关联测试、错误分类评审。

### 2.2 明确不做

- 不做 Provider 账户余额、账单金额或供应商专属消费接口；只采集响应中明确返回的 token usage。
- 不做 MCP、Skill、Prompt 管理。
- 不做自动故障转移、备用 Provider 队列、熔断或健康分数路由。
- 不在本版本交付 LaunchAgent、XDG/systemd 服务、macOS 签名公证、Linux 安装包或完整平台原生自启。
- 不改变客户端选择模型的方式，不引入独立的 Provider 切换状态。
- 不做通用客户端配置编辑器，不提供 Claude Code 无关偏好设置的编辑。
- 不提供 Codex 原始 catalog JSON 的编辑；catalog 中的模型元数据由 OneLLMRouter 生成，
  UI 只展示来源、可见性、顺序和生成状态。

## 3. Usage 数据契约

### 3.1 记录粒度

每一次上游尝试最多产生一条 Usage 记录。相同客户端请求在 Retry 中复用 `request_id`，通过 `upstream_attempt` 区分尝试。这样可以同时回答两个问题：

- 用户实际使用了哪个 Provider/模型以及消耗了多少 token。
- 重试发生了多少次，以及供应商是否在失败响应中报告了 usage。

没有明确 usage 字段时记录仍可写入，但对应 token 字段必须为 `null`，不得把未知值伪造为 `0`。统计命令默认只对有明确数值的字段求和，并同时返回 `unknown_records`。

### 3.2 统一字段

Usage 文件每行一个 JSON 对象，字段如下：

```text
time                RFC3339 时间，统一存 UTC
request_id          客户端请求的稳定 ID，Retry 尝试共享
provider            Provider prefix，例如 openai、anthropic
requested_model     客户端请求的完整模型名，例如 openai/gpt-5
upstream_model      实际发送给供应商的模型名
protocol            anthropic_messages、openai_chat、openai_responses
input_tokens        输入 token，整数或 null
output_tokens       输出 token，整数或 null
cache_read_tokens   cache read token，整数或 null
cache_write_tokens  cache write token，整数或 null
reasoning_tokens    reasoning token，整数或 null
usage_source        response、stream、translated_response 或 null
upstream_attempt    从 1 开始的上游尝试序号
status              success、error、cancelled 或 unknown
```

协议适配层负责从原始响应提取字段并保留“字段不存在”和“字段值为零”的区别。`CoreUsage` 当前只有 input/output（见 `internal/translate/core_types.go`），v1.5.0 应扩展协议中间层的可选字段，而不是在统计层猜测供应商字段。

### 3.3 采集边界

- 非流式响应：完整读取并成功解析响应后采集 usage；上游错误响应只有在明确包含可识别 usage 时才采集。
- Anthropic 流：使用最终 `message_delta` 等带 usage 的事件；没有该事件则保持未知。
- OpenAI Chat 流和 Responses 流：使用协议定义的 usage 事件或最终对象。
- 翻译路径：以供应商原始 usage 为准，不能因目标协议字段较少而丢弃可保留字段。
- Retry：每个尝试写入自己的 `upstream_attempt`；一次客户端请求不能因为重试而生成重复的“成功使用量”。
- 响应没有 usage 时不能调用本地 tokenizer 估算；估算能力不属于 v1.5.0。

### 3.4 存储与保留

默认目录：

```text
~/.onellm/usage/YYYY-MM-DD.jsonl
```

按 UTC 日期滚动文件。Usage 保留周期独立于现有 30 天运行日志；v1.5.0 不自动删除 Usage 文件，避免在尚未确定保留策略时造成不可恢复的数据丢失。写入采用追加方式，单条记录损坏不能阻止后续记录读取，统计命令应报告跳过的坏行数量。

文件不包含 API Key、Authorization、完整请求体或响应正文。写入失败不得影响已经成功返回给客户端的模型响应，但必须写入结构化错误日志。

## 4. 统计接口与口径

### 4.1 Core 命令

提供以下只读命令，均支持人类可读表格和 `--json`：

```text
onellm-router stats day [YYYY-MM-DD] [--json]
onellm-router stats week [YYYY-Www] [--json]
onellm-router stats month [YYYY-MM] [--json]
```

未指定日期时使用当前 UTC 日期、ISO 周或月份。命令必须在没有记录时返回空结果和零值，而不是错误。

### 4.2 返回维度

每个时间范围返回：

- `provider`、`requested_model`、`upstream_model` 的分组明细。
- `input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`reasoning_tokens` 总量。
- 每个 token 字段的未知记录数。

默认按 Provider、模型名称排序；不把不同模型的 token 合并成只有 Provider 一层的数字。若用户只关心 Provider，界面可以在同一数据集上折叠模型行。

### 4.3 时间与重复计数

- 周边界使用 ISO 8601：周一为一周开始，第一周遵循 ISO 定义。
- 聚合按记录的 `time` 字段，而不是文件名推断。
- 同一 `request_id + upstream_attempt` 视为唯一尝试；重复读取同一文件不得重复计数。
- 汇总所有明确报告 usage 的上游尝试，因为失败尝试也可能被 Provider 计费；本版本不提供请求结果或 Retry 分析视图。

## 5. Qt 配置界面

### 5.1 页面

- **Providers**：Provider 列表、名称、prefix、三种 Base URL、代理策略和 API Key 是否已设置。
- **Models**：按 Provider 管理模型；支持手动添加/删除和从对应 `/models` 端点发现；编辑 Codex reasoning 等模型能力字段。
- **Clients**：管理 Claude Code 模型槽位与 settings.json 同步，展示 Codex config/catalog 状态并提供受控操作。
- **Usage**：日/周/月切换、Provider/模型筛选和 token 分项统计。

### 5.2 Core 与 Qt 的配置边界

Qt 不直接解析或拼接 YAML。Core 增加机器可读命令：

```text
onellm-router config-get --json
onellm-router config-validate --json
onellm-router config-apply --stdin-json
```

约束：

- `config-get` 只返回 Provider/模型/客户端辅助所需的非秘密快照：`providers`、`codex.models`、
  `codex.overwrite_catalog` 和 `model_slots`；API Key 只返回 `api_key_set: true/false`。
- `config-validate --json` 从标准输入读取与 `config-apply --stdin-json` 相同的可编辑快照；
  `--json` 表示输出机器可读的校验结果，不是输入格式开关。
- 更新 API Key 时由用户在界面重新输入，Core 不回显旧值。
- Provider 的 `prefix` 是保留既有 API Key 时的身份键；省略 `api_key` 保留同 prefix 的旧值，
  修改 prefix 时必须显式提交新的 `api_key`。
- `config-validate` 在写入前执行现有 schema 和语义校验，并返回字段级错误。
- `config-apply` 只局部修改 `providers`、`codex.models`、`codex.overwrite_catalog` 和 `model_slots`，
  不得开放 Server、Log、Retry 或其他设置；必须原子写入、保留备份、脱敏日志，并保留未知字段和现有注释。
- 备份固定为所选配置旁的 `<config>.bak`，内容是写入前可恢复的原始 YAML，因此属于含密钥文件；
  必须保留原配置的文件权限，不得包含本次提交的新 API Key，也不得把旧或新 API Key 输出或记录到日志。
- 外部附着的 Core 只读，Qt 不得通过界面修改其配置。

### 5.3 配置变更生效

配置窗口保存后显示明确的“已写入配置，需重启 Core 生效”或“已热加载”状态，具体行为以 Core 能力为准。v1.5.0 不强制引入热加载；不应为了界面方便而自动停止外部实例。

### 5.4 客户端配置辅助

客户端辅助不是第二套 Provider 配置，而是把已经保存的 OneLLMRouter 配置安全地投影到客户端已有配置。

#### Claude Code

- 读取并展示 `~/.claude/settings.json` 的存在、解析和同步状态。
- 只允许写入 OneLLMRouter 管理的 `env` 键：`ANTHROPIC_BASE_URL`、`ANTHROPIC_AUTH_TOKEN`、
  `ANTHROPIC_MODEL` 以及 Opus、Sonnet、Haiku、Fable 四个默认模型键。`theme`、
  `skipWorkflowUsageWarning` 等无关偏好不由本产品管理。
- 合并时保留未知顶层字段和未知 `env` 字段；写入采用备份和原子替换，并提供状态检查与恢复。
- `ANTHROPIC_AUTH_TOKEN` 使用连接本地 Router 所需的固定非秘密占位值，不得把任何上游 Provider API Key
  写入 Claude Code 配置；Qt 和命令输出同样不得回显上游密钥。

#### Codex

- 展示 `~/.codex/config.toml`、OneLLMRouter catalog 和 Codex catalog 的路径、存在性、生成时间、模型数、
  来源 Provider 和同步状态；状态接口和 UI 为 OneLLMRouter 生成的条目显示来源标识，不修改 Codex catalog schema。
- 可编辑范围限于默认模型、已有 Codex reasoning 配置和 catalog 同步开关；不得编辑原始 catalog 元数据。
- 新配置优先直接引用 `~/.onellm/model-catalog.json`。现有 `overwrite_catalog` 行为继续兼容保留。
- 在确认存在能够保留 TOML 注释、未知字段、顺序和格式的可靠编辑方案前，不自动重写用户的 `config.toml`；
  首个实现可提供有效配置预览和可复制片段。

## 6. 跨平台基础架构

Go 和 Qt 均具备跨平台能力，但当前代码和发行链仍以 Windows 为前提：Go 主程序直接依赖 Windows Registry 和 `kernel32.dll`；Qt/构建链散落 `.exe`、注册表、自启、Restart Manager、`CREATE_NO_WINDOW`、ICO、MSVC、`windeployqt` 和 Inno Setup 假设。当前 `GOOS=linux go build` 已因 `golang.org/x/sys/windows/registry` 导入失败。

### 6.1 Go 边界

- 将 Windows Registry、自启和控制台处理拆分为 `platform_windows.go` 与 `platform_unix.go`（必要时增加 `platform_darwin.go`）。
- 公共命令只依赖平台接口，不直接导入 `windows/registry` 或调用 `kernel32`。
- Unix 实现先提供明确的 unsupported/no-op 返回值和可读错误，不伪装成已支持。
- 路径、临时目录、进程信号和文件权限通过平台接口集中处理。

### 6.2 Qt 边界

新增 `desktop/src/platform/`，集中以下能力：路径发现、Core 可执行文件名、子进程启动参数、自启、重启/退出和图标资源。

公共 Qt 代码不再散落 `Q_OS_WIN`、`.exe` 和注册表逻辑；Windows 适配器保留现有行为，非 Windows 适配器在本版本只提供编译通过且明确的未支持状态。

### 6.3 构建与验收

- Go CI 增加 Windows、Linux、macOS 的 `go test`/`go build` 矩阵。
- Qt CI 在 Windows、Linux、macOS 上完成配置和编译检查；需要 GUI 环境的测试使用离屏平台或只运行纯逻辑测试。
- 构建脚本将平台相关的打包步骤隔离；Windows Installer 继续使用 Inno Setup，不在本版本复制出其他平台安装包。
- CI 和发布验证使用 Go 1.26.x 最新稳定补丁版；`go.mod` 的 `go` 指令提升到 `1.26.0`。
- 通过 `rg` 检查公共源码中是否残留硬编码平台分支、绝对 Windows 路径和无条件 `.exe`。

## 7. Retry 评审结论

当前 Retry 与产品定位一致：用户显式选择了 `provider/model`，失败后重试同一 Provider/模型，行为可预测。自动 Failover 会把一次明确的 Provider 选择变成隐式路由，可能改变模型能力、计费和数据边界，因此不纳入 v1.5.0。

保留的默认策略：最多 15 次（含首次）、重试状态码 `408/409/425/429/500/502/503/504`、1 秒起步、30 秒单次上限、5 分钟总预算、jitter、遵守合法 `Retry-After`；流开始后不重放，Responses 容量错误只在输出开始前预检。

本版本只做三类工作：

1. 将每次 Retry attempt 与 Usage 记录关联，避免统计无法解释。
2. 补齐取消、超时、`Retry-After`、流开始边界和最终错误分类测试。
3. 依据测试或线上证据决定是否做局部参数/错误分类优化；没有证据则保持现状。

## 8. 实施顺序

### 阶段 A：Usage 数据契约与采集

- 扩展协议中间层的可选 usage 字段和 presence 语义。
- 在直通、翻译、流式、非流式和 Retry 路径写入 JSONL。
- 使用固定时钟/临时目录补充单元测试和端到端采集测试。

**完成标准**：三类协议的明确 usage 均能落盘；缺失字段为 `null`；Retry 不产生重复成功用量；日志和 Usage 文件不泄露密钥。

### 阶段 B：统计 Core API

- 实现按天、ISO 周、月读取和聚合。
- 输出 Provider/模型分组、token 分项、请求和 Retry 指标。
- 为空目录、跨天记录、坏行和重复记录增加测试。

**完成标准**：CLI 表格与 JSON 输出一致，重复运行结果稳定，周/月边界测试通过。

### 阶段 C：跨平台基础重构

- Go 平台适配拆分及 Unix 编译修复。
- Qt `desktop/src/platform/` 边界落地。
- CI 建立 Go 三平台编译矩阵和 Qt 平台检查。

**完成标准**：Windows 行为不回归；Linux/macOS Go 构建通过；公共 Qt 代码不依赖 Windows 专属 API。

### 阶段 D：Provider/模型配置界面

- Core `config-get`、`config-validate`、`config-apply`。
- Qt Providers/Models 页面、字段校验和模型发现。
- 原子写入、备份、未知字段/注释保留和外部 Core 只读测试。

**完成标准**：从界面创建或修改 Provider/模型后，Core 可加载并在 `/model` 列表中提供 `provider/model`；错误不会破坏原配置。

### 阶段 E：Usage 界面与发布回归

- Qt Usage 页面接入 `stats day/week/month --json` 或等价只读接口。
- 完成 Retry 回归、跨平台编译、配置编辑和 Usage 端到端测试。
- 更新中英文 README、CHANGELOG 和发布构建说明。

**完成标准**：Windows 桌面包可用；便携 Core 可独立运行；Usage 页面与 CLI 数值一致；本版本未引入 MCP/Skill/Prompt 或 Auto Failover。

### 阶段 F：Go 工具链升级与最终发布门禁

- 将 `go.mod` 的最低 Go 版本提升到 `1.26.0`，CI 和发布环境统一使用 Go `1.26.x` 最新稳定补丁版。
- 保持现有依赖版本，只有在 Go 1.26 验证明确发现兼容性问题时才单独处理依赖。
- 在 Windows、Linux、macOS 上重新执行 Go 测试/构建，并复跑 Qt、安装器和发布安全门禁。

**完成标准**：Go 1.26.x 最新稳定补丁版下全量 Go、race、vet、模块校验、三平台构建和现有 Qt/Windows 发布门禁通过；工作区无临时工具链文件或未声明的依赖升级。

### 阶段 G：客户端配置辅助与最终发布回归

- 先冻结 Claude/Codex 状态与写入契约，并验证 TOML 编辑能否保留注释、未知字段和顺序。
- Core 实现 Claude settings.json 的受控合并、备份、恢复和状态检查。
- Core 实现 Codex 配置/catalog 状态、来源标识和重新生成；TOML 自动写入取决于前置验证，否则只提供预览与片段。
- Qt 增加 Clients 页面，将 Claude 模型槽位从 Models 页面移入 Claude Code 区域；Codex reasoning 仍只在 Models 页面编辑。
- 重新执行 v1.5.0 全量发布回归并更新中英文文档。

**完成标准**：Claude Code 不再需要人工合并 OneLLMRouter 管理的 JSON 字段；Codex 可明确看到有效模型和 catalog 来源，且不会因为本产品写入而丢失用户 TOML 内容；Qt/Core/测试均不泄露 Provider API Key。

| Retry | attempt 关联、取消、预算、Retry-After、流开始后不重放 |
| 配置界面 | Provider 字段、模型增删/发现、校验失败不破坏配置、API Key 不回显 |
| 客户端辅助 | Claude 受控 JSON 合并/恢复；Codex 状态、来源标识和安全 TOML 决策；真实用户目录不被测试修改 |
| 跨平台 | Go Windows/Linux/macOS 构建；Qt 公共层无 Windows 硬编码 |
| Go 工具链 | `go.mod` 为 `1.26.0`；CI/发布使用最新 `1.26.x` 补丁版；全量 Go 与 Qt/发布门禁通过 |
| 回归 | `go test ./...`、`go test -race ./...`、`go vet ./...`、Qt 测试与 `git diff --check` |

## 10. 风险与取舍

- 各 Provider 的 usage 字段并不完全同构；必须保留可选字段和来源，不能用一个“标准 token 算法”替代上游事实。
- Retry 失败响应可能带 usage，默认统计会包含这些尝试；界面必须区分“所有上游尝试”和“最终成功请求”。
- 配置文件可能含未知字段和用户注释，完整 YAML 重序列化会造成无关 diff；因此配置写回是独立的高风险模块。
- 跨平台基础与完整平台产品是两项不同工作；本版本只移除编译和架构层面的 Windows 耦合，不承诺非 Windows 的自启和安装体验。
- Go 1.26 默认启用新的 Green Tea GC，并调整了少量标准库行为；必须复跑代理长生命周期、流式请求、取消/关闭和跨平台构建测试，不能只依赖编译通过。
- Go 1.26 是 macOS 12 的最后支持版本；本版本不因工具链升级扩大平台支持承诺。
- Claude settings.json 可用结构化 JSON 合并安全管理允许字段；Codex config.toml 更强调注释和人工维护格式，
  未通过保留性验证前只能提供预览，不能为了“一键配置”承担破坏用户文件的风险。
