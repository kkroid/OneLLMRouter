# OneLLMRouter v1.5.0 Client Integration Design

> Status: approved T12 contract (2026-08-10)
>
> Baseline: `4e780e9`
>
> Decision: Claude Code controlled merge is allowed; Codex `config.toml` rewriting is not.

## 1. Scope And Decision

This record freezes the Core contracts consumed by T13-T15. Client assistance projects the existing
OneLLMRouter configuration into Claude Code and Codex; it is not another Provider configuration source.

The Codex TOML **mutation/serialization** gate is **NO-GO** for v1.5.0.
`github.com/pelletier/go-toml/v2` v2.4.3 retained unknown values semantically in the bounded spike, but a
decode/mutate/encode cycle did not retain comments, the multiline-string representation, or key order. Its
stable decoder is approved as T14's production read-only parser because status never serializes or writes the
parsed document. Its AST parser is explicitly unstable and does not provide a supported source-preserving
mutation contract. T14 therefore:

- may add `github.com/pelletier/go-toml/v2` v2.4.3 to `go.mod` and `go.sum` solely for read-only status parsing;
- must not write, replace, back up, or restore Codex `config.toml`;
- parses the complete TOML document and projects only status fields, ignoring unknown fields semantically;
- provides status, preview, and a copyable safe snippet; and
- may atomically regenerate catalog JSON through the existing catalog generator.

## 2. Shared CLI And JSON Contract

Commands use the existing global `--config <router-yaml>` option to select the OneLLMRouter configuration.
Client-path overrides are for tests, explicit recovery, and advanced use; normal operation uses the current
user home. Every command below requires the stated machine-output flag and writes exactly one JSON object to
stdout followed by a newline.

The common envelope is:

```json
{
  "schema_version": 1,
  "client": "claude",
  "operation": "status",
  "ok": true,
  "errors": [],
  "result": {}
}
```

The fields are always present. `schema_version` is the integer `1`. `client` is `claude` or `codex`.
`operation` is the command leaf name. `errors` is an array of objects with exactly `code`, `message`, and
`path`; `path` is `null` when no file is implicated. Messages are bounded and secret-safe. `result` is always
an object, including on failure. Arrays are empty rather than `null`; fields declared `string/null` use JSON
`null` when unknown. Defined error codes are `invalid_arguments`, `router_config_error`, `unsafe_path`,
`settings_invalid`, `settings_unreadable`, `backup_missing`, `backup_invalid`, `backup_unreadable`,
`write_failed`, `config_unreadable`, `catalog_invalid`, `catalog_unreadable`, `catalog_generation_failed`, and
`catalog_write_failed`. New codes require a schema-version review rather than ad hoc UI string matching.

An expected state such as an absent or invalid client file is represented in `result`, not as a command
failure. The process exits `0` when `ok` is `true`. Invalid arguments, unreadable required Router
configuration, unsafe paths, or failed requested mutations return the same envelope with `ok: false` and exit
`1`. No command returns an API key, authorization value, complete client file, backup bytes, or arbitrary raw
client configuration. Preview is the sole exception for generated text: it returns only the fixed,
non-secret TOML snippet defined below. In machine mode, expected errors are encoded in the envelope; Cobra
usage and duplicate free-form errors are not written to stderr.

## 3. Claude Code Contract

### 3.1 Commands

```text
onellm-router client claude status --json [--settings <path>]
onellm-router client claude apply --json [--settings <path>]
onellm-router client claude restore --json [--settings <path>]
```

The default settings path is `<user-home>/.claude/settings.json`; the fixed backup path is
`<settings-path>.bak`. `apply` takes no client values from stdin or flags. It derives all managed values from
the selected OneLLMRouter YAML so the Router remains the single source of truth.

### 3.2 Managed Keys

Only these seven keys under the top-level `env` object are managed:

```text
ANTHROPIC_BASE_URL
ANTHROPIC_AUTH_TOKEN
ANTHROPIC_MODEL
ANTHROPIC_DEFAULT_OPUS_MODEL
ANTHROPIC_DEFAULT_SONNET_MODEL
ANTHROPIC_DEFAULT_HAIKU_MODEL
ANTHROPIC_DEFAULT_FABLE_MODEL
```

`ANTHROPIC_BASE_URL` is `http://localhost:<http_port>/anthropic` using the selected Router configuration.
`ANTHROPIC_AUTH_TOKEN` is the exact fixed string `x`. It is a non-secret local compatibility placeholder and
must never be replaced with an upstream Provider key. The five model values come from `model_slots.default`,
`opus`, `sonnet`, `haiku`, and `fable` respectively.

The input must be absent or a JSON object. An absent `env` creates an object. An existing `env` must be an
object or apply refuses to write. Apply replaces the seven managed values and preserves every unknown
top-level member and every other `env` member semantically. It does not manage `theme`,
`skipWorkflowUsageWarning`, permissions, hooks, MCP, Skills, Prompts, or any other Claude preference.

### 3.3 Claude Result

All three operations return these `result` fields:

| Field | Type | Contract |
| --- | --- | --- |
| `settings_path` | string | Absolute selected path. |
| `backup_path` | string | Absolute `<settings_path>.bak` path. |
| `exists` | boolean | Whether settings existed when inspected. |
| `backup_exists` | boolean | Whether the backup existed when inspected. |
| `parse_state` | string | `absent`, `valid`, `invalid`, or `unreadable`. |
| `sync_state` | string | `absent`, `current`, `different`, `invalid`, `unreadable`, or `unknown`. |
| `managed_key_count` | integer | Always `7` after Router configuration loads. |
| `configured_model_count` | integer | Count of distinct non-empty values in the five Router model slots. |
| `changed` | boolean | Whether this operation changed settings. |
| `backup_created` | boolean | Whether apply replaced the one-level backup in this operation. |
| `atomic_replaced` | boolean | Whether this operation atomically replaced settings. |

Status always sets the three operation fields (`changed`, `backup_created`, and `atomic_replaced`) to
`false`. Apply reports the post-operation parse and sync states. Restore reports the state of the restored
bytes relative to current Router values; a successful restore may therefore be `different`.

### 3.4 Backup, Apply, And Restore

- If settings are already `current`, apply is a no-op and does not rotate an existing backup.
- If settings are absent, apply creates the parent directory with user-only permissions where supported,
  writes a new settings file atomically, and creates no backup because no pre-apply bytes existed.
- If settings are valid and different, apply writes the exact pre-apply bytes to `<settings>.bak`, replacing
  any older one-level backup, before replacing settings. If backup creation fails, settings is unchanged.
- Invalid or unreadable settings are never overwritten. Apply returns `ok: false` without changing settings
  or backup.
- Backup and temporary files are created in the destination directory. Each new file is flushed and closed
  before a same-directory atomic rename; the directory is synchronized where the platform supports it. Backup
  replacement completes before settings replacement. Existing settings permissions are retained; newly
  created files and backup files use user-only permissions where supported. Temporary files are removed on
  failure.
- A backup can contain user secrets. Its contents, hashes, or excerpts never appear in stdout, stderr, or logs.
- Restore requires an existing backup whose bytes parse as a JSON object with an absent or object-valued
  `env`. It refuses a missing, unreadable, or malformed backup and leaves settings unchanged.
- Restore atomically replaces settings with the exact backup bytes. It does not create another backup and
  retains `<settings>.bak`, so repeating restore is idempotent.
- Because an absent pre-apply file has no exact bytes to back up, restore after first-time creation returns
  `ok: false` with error code `backup_missing`; it does not delete the new settings file.

## 4. Codex Contract

### 4.1 Commands

```text
onellm-router client codex status --json [--codex-config <path>] [--onellm-catalog <path>] [--codex-catalog <path>]
onellm-router client codex preview --model <provider/model> --json [--codex-config <path>] [--onellm-catalog <path>] [--codex-catalog <path>]
onellm-router client codex catalog-apply --json [--codex-config <path>] [--onellm-catalog <path>] [--codex-catalog <path>]
```

Defaults are `<user-home>/.codex/config.toml`, `<user-home>/.onellm/model-catalog.json`, and
`<user-home>/.codex/model-catalog.json`. There is deliberately no Codex `config-apply` or `restore` command.
`catalog-apply` means regenerate catalog JSON using the existing deterministic generator; it never means
apply TOML.

### 4.2 Codex Result

All three operations return these `result` fields:

| Field | Type | Contract |
| --- | --- | --- |
| `config_path` | string | Absolute selected `config.toml` path. |
| `config_exists` | boolean | Whether `config.toml` exists. |
| `config_parse_state` | string | `absent`, `valid`, `invalid`, or `unreadable`. |
| `config_sync_state` | string | `absent`, `current`, `different`, `invalid`, or `unreadable`. |
| `onellm_catalog_path` | string | Absolute OneLLMRouter catalog path. |
| `onellm_catalog_exists` | boolean | Whether that catalog exists. |
| `codex_catalog_path` | string | Absolute legacy Codex catalog path. |
| `codex_catalog_exists` | boolean | Whether that catalog exists. |
| `catalog_sync_state` | string | `absent`, `current`, `different`, `invalid`, or `unreadable`. |
| `catalog_generated_at` | string/null | RFC3339 UTC modification time of the OneLLMRouter catalog, or `null`. |
| `model_count` | integer | Valid OneLLMRouter catalog model count; otherwise `0`. |
| `effective_model` | string/null | Valid parsed top-level `model`, or `null`. |
| `effective_provider` | string/null | Prefix before `/` in `effective_model`, or `null`. |
| `configured_model_provider` | string/null | Valid parsed top-level `model_provider`, or `null`. |
| `source_providers` | array | Sorted distinct prefixes from valid catalog model IDs. |
| `source_tag` | string | Exact display-only value `OneLLMRouter`. |
| `overwrite_catalog` | boolean | Effective Router `codex.overwrite_catalog` value. |
| `config_write_supported` | boolean | Always `false` in v1.5.0. |
| `written_paths` | array | Absolute paths written by this operation; otherwise empty. |
| `snippet` | string/null | Preview's generated snippet; `null` for other operations. |

The stable `source_tag` is UI/status provenance only. It must not be inserted into Codex `config.toml`, the
Codex catalog schema, or model metadata. `catalog_generated_at` is file metadata, not a catalog schema field.

Status parses the complete document with `github.com/pelletier/go-toml/v2` v2.4.3's stable decoder into a
read-only status projection. The decoder must not reject unknown keys; unknown top-level fields, tables, and
provider fields are ignored semantically and are never returned. Any TOML syntax error or incompatible type
for a projected field produces `config_parse_state: "invalid"` and `config_sync_state: "invalid"`. An I/O
failure produces `unreadable` for both states. Status never marshals, rewrites, or normalizes the file.
Projected config values are `null` when the file is absent, invalid, unreadable, or the valid document omits
the corresponding optional field.

`config_sync_state` is `current` only when the valid parsed document has `model_provider = "onellm"`,
`model_catalog_json` equal to the absolute OneLLMRouter catalog path, and a provider table named
`model_providers.onellm` with `name = "OneLLMRouter"`, the expected local Responses endpoint,
`wire_api = "responses"`, and `requires_openai_auth = true`. Any missing or different required value is
`different`. The parsed top-level `model` and `model_reasoning_effort` remain display-only status values and do
not affect synchronization.

### 4.3 Preview And Copyable Snippet

Preview validates that `--model` is a configured namespaced Responses model and returns this complete snippet
with platform-correct TOML string escaping and the absolute OneLLMRouter catalog path:

```toml
model = "<provider/model>"
model_provider = "onellm"
model_catalog_json = "<absolute onellm catalog path>"

[model_providers.onellm]
name = "OneLLMRouter"
base_url = "http://localhost:<http_port>/openai/v1"
wire_api = "responses"
requires_openai_auth = true
```

The user decides how to merge the snippet. Preview does not promise that the table name is conflict-free in an
existing file, and it never edits the file. Codex reasoning remains editable only in OneLLMRouter's existing
`codex.models` configuration; preview may display a valid parsed `model_reasoning_effort`, but it does
not generate or manage that Codex preference.

`catalog-apply` always atomically writes the OneLLMRouter catalog. It writes the legacy Codex catalog only when
`codex.overwrite_catalog` is `true`. Catalog generation must complete discovery and produce at least one model
before either existing catalog is replaced. `written_paths` names only successful writes. No `config.toml`
backup is created because `config.toml` is never written.

## 5. TOML Preservation Spike

The bounded spike used `github.com/pelletier/go-toml/v2` v2.4.3 in a disposable module under Go
`1.26.0 windows/amd64`. The module declares Go 1.21 compatibility and uses the MIT license. The version was
available from the configured Go proxy, and the upstream repository HEAD was reachable during the check.

The synthetic fixture contained no real paths or credentials. It covered:

- leading and inline comments;
- unknown top-level keys and an unknown table;
- deliberate key and table ordering;
- a triple-quoted multiline string;
- `model`, `model_provider`, `model_reasoning_effort`, `approval_policy`, `sandbox_mode`, and
  `model_catalog_json`;
- a `model_providers` entry with `name`, `base_url`, `wire_api`, and a fake environment-variable name; and
- a representative project trust table.

The fixture parsed successfully and unknown values survived semantically. Re-encoding removed comments,
changed the multiline representation, and changed key order, so byte preservation failed. The focused test,
race test, and vet check passed while asserting those observed results. The disposable spike directory and its
module files are intentionally not part of the repository.

This evidence is sufficient for the v1.5.0 mutation gate: no automatic Codex TOML rewrite and no production
TOML dependency for writing. The reviewed v2.4.3 stable decoder is approved for production read-only status
parsing, where comment, formatting, and ordering preservation are irrelevant because no bytes are serialized.
A future release may revisit writing only with a maintained, stable source-editing API and fixtures proving
preservation during actual targeted mutation, not merely parse/encode semantic equivalence.

## 6. Test Isolation And Secret Safety

- Every client-file test sets a temporary user home before path resolution and passes explicit client paths
  inside that directory where practical.
- Tests fail before running if a resolved settings, config, backup, temporary, or catalog path escapes the
  test root. They never read, stat, copy, or write the real `~/.claude` or `~/.codex` trees.
- Environment variables must be restored by test cleanup. Tests do not run in parallel when they mutate
  process-wide home variables.
- Fixtures use obvious fake values and environment-variable names, never captured user configuration or API
  keys. Secret-leak assertions cover stdout, stderr, returned errors, and logs.
- Failure injection operates only on fixture paths. Atomic-write tests verify exact pre-operation bytes after
  failure and remove their own temporary files.
- Catalog tests use fake Providers and `httptest` or isolated loopback listeners; they do not contact real
  Providers, bind the production port, or start/stop an installed Router.

## 7. Explicit Non-Goals

v1.5.0 does not include production writes in T12 itself, a generic client configuration framework, arbitrary
Claude preference editing, a raw TOML editor, raw catalog JSON editing, Qt parsing of JSON/TOML client files,
MCP/Skill/Prompt management, Auto Failover, per-provider switching state, hot reload, or replacement of either
client CLI. An externally attached Core remains read-only in Qt.

## 8. Remaining Design Gaps

- The fixed preview provider name `onellm` can conflict with a user-owned table. v1.5.0 reports the conflict and
  leaves manual merging to the user rather than inventing a destructive rename workflow.
- Restore cannot represent a pre-apply absent Claude file without a second metadata format. First-time creation
  therefore has no automatic delete-based undo.
- Catalog schema/template compatibility remains coupled to the supported Codex version. Generation errors are
  surfaced and existing catalogs are retained; v1.5.0 does not infer missing future metadata.
